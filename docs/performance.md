# 性能参考

本页记录 Jetson AGX Orin 64GB / CUDA SM87 上的实测参考，各节注明测量日期。2026-10-12 的机器为 MAXN 模式、GPU 频率 1300.5 MHz；测试未修改全局功耗或频率设置。结果对应 Rust release CLI 和匹配的优化执行包；执行库、kernel 或 ABI 变化时需重建执行包，单独更新 CPU 调度可复用原执行包。表中的 tokens/s 均按实际 token 数计算。

## 正式构建入口与真实矩阵调优（2026-10-15）

`tools/model/flash_next/build.py` 从当前原生模型的绑定、权重几何和 host ABI 构造整数算子，原始权重逐字节复用。119 组 Q4/W8/融合 SwiGLU 几何覆盖 4392 处绑定；两种真实 E8P 专家矩阵分别验证 8/16 行 tile，保留输入的联合路由选择。构建对象原子缓存，已验证 119 项命中、损坏单项重建和最终发布记录丢失后的恢复。

prefill 根据模型声明的程序识别，使用 512/2048/4096 行负载测量；动态短行、非对齐尾部、容量上限和更改输入后的 Graph replay 另行校验。统一候选包括合法的 128 行 tile 和 Q4 K=256/单级流水，避免因搜索空间缺项丢失既有性能；不存在按请求长度手写的实现分界。已验收包可用 `--prefill-only` 单独重建这部分。

## Flash Next 配置

使用官方 checkpoint 构建的文本模型：自有整数 E8P Q2A8 专家、Q4A8 输入投影与输出头、W8 输出投影与共享 FFN，精度敏感路径保留 BF16/FP16/FP32。专家全量常驻，KV 为 group-64 INT8，GDN 持续状态为 FP32。测试不含图片、其他并发请求或历史续写草稿。

完整代码生成通过 `orinfer serve` 的流式 Chat Completions API 执行，覆盖实际 chat template、请求调度、状态恢复、MTP 和 CUDA 计算。Python 客户端只发请求、接收 SSE 和计时。服务配置：

```bash
./target/release/orinfer serve /path/to/optimized-flash-next \
  --model qwen-flash-next --cuda-graph decode_only \
  --resident-experts full --mtp-drafts 3 \
  --prefix-cache-mib 1024 --memory-reserve-mib 512
```

关闭 MTP 的对照使用相同执行包和配置，只将 `--mtp-drafts` 改为 `0`。草稿长度使用正常的请求级自适应策略，没有固定验证宽度。

请求参数为 `enable_thinking=true`、`reasoning_effort=medium`、`temperature=0`、`seed=20261002`、`thinking_token_budget=16384`、`max_completion_tokens=16384`。思考和代码共享 16K 总输出上限；API 为思考结束标记和至少一个答案 token 预留空间。

场景要求从零实现安全 Rust 流式帧解码器：大端 u32 长度头、任意碎片输入、最大帧限制、复位和标准库单元测试。提示包含与实现无关的仓库参考 helper，以构造不同输入长度。完整请求测试的输入分别为 512、2048、8191 tokens；下方独立 prefill 测试使用严格的 512、2048、8192-token 输入。

## 完整代码生成

每种输入、每个 MTP 配置各运行一次首请求和一次相同提示的完整 prefix 命中请求。下表采用后者的暖态数据，每格为一次完整请求的测量值。生成 6176–7598 tokens，包含思考和代码；所有请求均自然结束，`finish_reason=stop`。

| 输入 tokens | 实际输出 tokens | MTP 关闭 decode TPS | MTP 开启 decode TPS | 加速比 | MTP 思考阶段 TPS | MTP 代码阶段 TPS | 草稿接受率 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 512 | 6276 | 29.72 | 44.99 | 1.51× | 41.46 | 49.37 | 74.8% |
| 2048 | 6176 | 29.64 | 45.21 | 1.53× | 44.02 | 46.62 | 76.4% |
| 8191 | 7598 | 29.49 | 45.82 | 1.55× | 43.14 | 49.30 | 77.4% |

Decode TPS 为 `(completion_tokens - 1) / (完整 HTTP 请求耗时 - TTFT)`，包含 Rust 调度、token 传输、同步与 SSE 尾部处理；只统计提交的 tokens，包含思考，不统计被拒绝的草稿。TTFT 从发请求计时，到收到首个有效思考或正文片段。SSE 片段可能合并多个 tokens；阶段 TPS 按 API usage 和思考/正文片段时间边界近似计算，不将片段数当作 token 数。

完整请求的 decode 为约 45 TPS，代码阶段为 46.62–49.37 TPS；这些结果没有达到完整请求 50 TPS，不能用代码阶段吞吐替代包含思考的完整 decode。

两种 MTP 配置下，全部请求的思考文本、代码、token 数和停止原因一致。三个输入长度生成的代码均可编译；512 与 8191-token 场景的生成单元测试全部通过。2048-token 场景有一个生成测试重复输入首个帧头字节，原始结果为 10 通过、1 失败；仅修正该测试输入、保持生成的解码器实现不变后，11 项通过。这验证了本次 MTP 开关的一致性，不替代独立 BF16/FP8 量化质量评估。

## Prefill 与无缓存 API 首 token

执行层通过 `orinfer run-model` 测量，关闭 MTP 和 prefix 复用，每种长度一次预热后取三次测量均值，仅生成首 token。`prefill_s` 包含模型主干、输入传输和同步，输出头与首 token 选择单独计时。

本节的历史执行包在 prefill 输入投影中使用保留的 W8 矩阵，decode 使用 Q4。后续统一 Q4 prefill 路径的数据见下方动态模板测量。

API 测量通过 `orinfer serve`，设置 `--prefix-cache-mib 0`。每种长度一次首请求后取两次测量均值，确认 cached tokens 为 0。为测首 token 而将探针输出上限设为 8 tokens；这些短探针的 decode 或正文阶段速度不用于代码生成性能验收。服务已加载就绪，TTFT 不含模型加载。

| 输入 tokens | 执行层 prefill TPS | API TTFT：MTP 关闭（秒） | API TTFT：MTP 开启（秒） | 输入 / API TTFT：MTP 关闭 TPS | 输入 / API TTFT：MTP 开启 TPS |
| --- | --- | --- | --- | --- | --- |
| 512 | 1008.9 | 0.509 | 0.573 | 1005.2 | 893.3 |
| 2048 | 899.9 | 2.283 | 2.424 | 897.0 | 844.8 |
| 8192 | 906.8 | 9.053 | 9.544 | 904.9 | 858.4 |

输入 / API TTFT 包含请求处理、prefill、首 token 选择和 MTP 初始草稿预热，不能等同于模型主干 prefill TPS。MTP 增加的 TTFT 分别为 63.8、141.2、490.4 ms；记录的草稿初始预热分别为 63.3、138.0、475.9 ms，占增加时延的约 97%–99%。两条计时路径分开测量，不能把不同运行的阶段耗时直接相加。

另一个固定长度的 `run-model` 短输出基准使用 512-token 输入、128-token 输出，关闭 MTP 和缓存；预热后取三次测量均值，执行层 prefill 为 1008.39 TPS、decode 为 30.43 TPS。此项对应固定 token-ID 请求，独立于上方通过 Chat API 生成数千 tokens 的 thinking 代码场景。

## 原生绑定目录迁移

同一套 Flash Next 权重与 cubin，迁移前后完整执行 manifest（60,658 条绑定、所有程序、参数、偏移及状态契约）逐字段一致。执行包 JSON 从 61.08 MB 降至 1.57 MB，只保存 1,297 个编译定义、883 份不同 cubin 的身份和 256 个共享动态 launch 模板。逐层张量角色和绑定表编译进原生库，库由 1.94 MB 增至 17.10 MB；完整绑定和程序通过有 owner 的 C 数组导出，不经过 JSON 往返。

Rust release CLI 的同机对照，512-token 输入、128-token 输出，后三次请求取平均：

| 指标 | 迁移前 | 迁移后 |
| --- | ---: | ---: |
| 加载到可工作 | 19.14 s | 18.97 s |
| 首请求 TTFT | 898.5 ms | 594.2 ms |
| prefill | 1009.02 TPS | 1008.84 TPS |
| decode，MTP 关闭 | 30.39 TPS | 30.40 TPS |
| 固定 GPU buffer 分配 | 42,531,274,022 B | 42,531,274,022 B |
| 进程峰值 RSS | 1013.61 MiB | 1028.82 MiB |

加载和首请求各为一个样本，受文件缓存、驱动初始化和 I/O 波动影响；本次目录缩减没有体现为显著启动提速。稳态吞吐基本持平，GPU 分配不变，宿主峰值 RSS 约增加 15.2 MiB，原生库包含新增的静态绑定表。

真实 SSE Chat 请求另复测 512-token 输入、medium thinking、16K 总输出预算、MTP 3 草稿和 1 GiB prefix cache。实际输出 6,276 token 后自然结束，thinking 与代码内容均和迁移前完全一致；完整稳态 decode 为 45.19 TPS，512-token prefix 全命中 TTFT 为 15.36 ms，状态恢复为 5.66 ms。该独立 API 进程的 Model Ready 为 29.87 s，说明启动存在较大的运行间波动，不能用单次 CLI 对照保证部署提速。

额外通过普通生成的 151 个完整状态范围、MTP/prefix 的 159 个状态范围精确对照，MTP 1–7 草稿及各接受长度、2–31 活跃请求的固定/动态 batch、取消和槽位复用验证；动态 launch 的行数契约覆盖 2–128。通用 C 包夹具也覆盖 off/decode_only/full 三种 Graph 模式和改变输入后的 replay。


## 多请求 MTP 与混合调度

2026-10-12，使用相同官方权重与 Rust release CLI 服务参数，对照原混合 HC 部署与增加 decoder 子组、批量 MTP、计划缓存及 VMM 前缀共享的开发构建。这是整个部署的对照，包含执行包与运行时变化。服务为 `decode_only`、MTP 草稿上限 3、prefix cache 12288 MiB、预留 512 MiB、prefill 预算 350 ms、TPOT 软目标 400 ms；没有修改机器频率或功耗。

并发请求使用完整命中的 59-token Rust 代码生成提示，开启 medium thinking、greedy、seed20261002，总输出上限 128 tokens。各档测两次，下表列第二次；这是短 thinking 请求的实际提交 tokens / 完整 HTTP 轮次耗时，包含调度和流式传输，不是完整代码任务或纯 GPU decode TPS。

| 活跃 decoder | 原包总输出 TPS | 新包总输出 TPS | 新包 MTP 轮次 |
| --- | ---: | ---: | ---: |
| 2 | 40.61 | 40.05 | 3 |
| 4 | 71.57 | 70.39 | 3 |
| 8 | 115.55 | 109.76 | 2 |

新调度器先测普通 batch 的平均成本，再以完整 MTP 成本、有效提交量和误差余量决定收益。该短 thinking 场景中的 MTP 收益较低，因此多数轮次回退普通 batch；少量探测仍有成本。上述数据不证明普遍吞吐提升。

| decoder 数 | 原包冷请求 TTFT（秒） | 新包 TTFT（秒） | 原包最大片段间隔（ms） | 新包最大片段间隔（ms） |
| --- | ---: | ---: | ---: | ---: |
| 2 | 4.204 | 4.115 | 525 | 505 |
| 4 | 4.061 | 4.122 | 304 | 294 |

片段间隔只统计冷请求等待首 token 时的重叠区间。MTP 和 UTF-8 解码可以合并多个 token，因此这些值不是逐 token ITL，也不构成硬 SLO。混合迭代仍使用真实的 16/128-token 块和 M1 尾部。

GPU 对照覆盖 2/3/4/8 路独立草稿、共享目标验证、各接受长度、前缀分支恢复与更换成员后的共享图。草稿概率对照一致，混合 decoder 子组与原混合包的概率差异接近浮点舍入误差。验证临时 prefix/因子存储在同一请求内按最大宽度复用，每请求由 115.07 MiB 降至 26.30 MiB，权重与计算精度不变。

实际 Chat API 另验证图片、多图，以及 medium thinking、16K 总输出上限的 Python 归并排序。最终构建自然结束，输出 828 tokens（其中思考 636），生成函数通过空数组、重复值、负数、逆序和固定 seed 随机列表测试；重复请求命中完整 66-token 提示。该检查验证执行与状态复用，不替代独立 BF16/FP8 量化评估。

前缀恢复进一步使用固定地址的 VMM 共享映射。本机最小物理粒度为 2 MiB；保存检查点时合并不足一页的末尾碎片，完整区间只读共享，写入前复制。真实模型在修改后续输入的情况下，对照未命中路径的续写以及完整 KV/GDN/卷积/MTP 状态：

| 恢复检查点 | 共享 KV 物理区间 | 恢复耗时 |
| --- | ---: | ---: |
| 4096 tokens | 48 MiB | 4.95 ms |
| 8192 tokens | 100 MiB | 6.37 ms |

## 共享大行数、视觉与 MTP 入口收敛

共享 target／draft 的 Q4、W8、BF16、HC 与专家动态行选择改为离线实测生成，移除原先手写的 32／128 行性能分界。路由及专家上下投影共同选择，保留同一 tile 布局；七个既定整数 AOT 行数特化继续共用源码模板。相同动态实现只保留一个默认绑定，合并时保留原始 launch 表达式及 token 到专家行的倍率。

HC injection 原有并行 FP32 求和与 Tensor Core 的归约顺序不同，不能作为数值相同的候选。窄输出直接 MMA、矩阵 tile 和单行参考现在统一采用 BF16 MMA K16 累加顺序。98 份真实矩阵、838 个矩阵／长度组合逐位一致，覆盖非对齐尾部；候选验证还包含修改输入后的 Graph replay。五种 tile 选中两种，其他候选不发布，边界来自测量。FP64 算子参考、修改权重后的回放及输出尾部保护检查通过。

视觉从六个容量程序合为一个动态 patch 程序，merger 按真实 patches 的四分之一执行。4／140／256／540／1024／3072／8192 patches、修改输入后的 full Graph 回放及多图顺序，与原编码器特征逐位一致。视觉容量独立声明，文本和 MTP 程序的长度上限不随之扩大。

MTP 验证、恢复和捕获从 21 个按长度包装合为三个入口，真实长度为 2–8。草稿、warm 和状态快照继续按执行用途区分。映射 KV 之前先写入实际验证长度；验证输入统一使用容量 arena，所有状态算子仍接收实际长度。schema 和 C ABI 保持版本 1。

最终包为 445 个编译定义、383 个唯一 cubin、14,780 项展开绑定，上一包分别为 525／388／17,265。权重及全部 buffer 描述逐项未改；常驻分配为 41,954,490,864 bytes，容量仍为 49,605,600,400 bytes。

同一组 Rust release 完整请求链、16 个计时步的普通 decode 总吞吐如下：

| 并发 | 上一包 TPS | 收敛后 TPS |
| --- | ---: | ---: |
| 1 | 25.93 | 26.20 |
| 2 | 42.53 | 43.42 |
| 4 | 70.86 | 73.90 |
| 8 | 102.44 | 112.64 |
| 33 | 159.64 | 164.63 |

Rust release CLI 加载到就绪 18.39 s；512-token 请求排除一个首请求后，三个热态请求合计 981.8 TPS，上一包为 985.6–988.1 TPS。

两组 64-token 自由生成的自适应 MTP 为 37.21／47.45 TPS，上一包为 43.86／49.34 TPS。第一组生成轨迹改变，接受草稿由 37/50 降为 33/53，轮次由 25 增为 29；第二组输出及接受数相同，验证总耗时增加约 4.5%。本轮普通 decode 有提升，但 MTP 仍存在这项性能回退。

单行参考也统一了 injection 归约，因此另用旧包作固定历史对照：两组代码场景各 64 个位置、seed 20261002，共 128 个位置中 top-1 相同 126 个，candidate top-1 全在旧包 top-3 内；目标 NLL 均值变化 −0.000345，最大增加 0.09784、最大降低 0.13119。该对照用于检查执行重组，量化权重未改。

单流提交状态与新参考逐位一致；28 个混合对照、多路验证／草稿、Graph／槽位复用及 105 个接受前缀／拒绝后缀状态检查通过。文本、单图和双图分别验证 1–7 个草稿，贪心输出与该包的普通生成一致，固定 seed 回放一致。4093→6141-token 长前缀恢复、8192-token 长短请求调度通过；后者固定历史 KL／NLL 差为 0。

## MTP 验证复用 packet

模型声明支持 batch 验证时，单请求也使用 Verification packet，复用动态行计算、请求状态绑定和完整 Graph。共享片段与完整 packet 使用同一套分支捕获：只启用片段完整覆盖的 fork/join；连续辅助 kernel 归属其原始槽位，重复私有状态槽位不影响无关共享分支。节点优先级使用实际 launch grid。

HC injection 的窄行实现通过复制未使用的 MMA 行／列消除循环内条件加载，并按对齐的 BF16 对读取共享内存，保留原 K16 累加顺序。1–4 行的单算子耗时从约 26 μs 降至 19 μs；98 份真实矩阵、838 个矩阵／长度组合与原矩阵实现逐位一致。FP16／BF16、单输出门控、非对齐尾部和修改输入／权重后的 Graph 回放检查通过。离线选优仍只发布 tiny1、bulk16，未选中的实现不进入执行包。

两组 64-token 代码生成，seed 20261002、最多三个草稿、自适应宽度、decode_only Graph，Rust release 完整请求链排除最初三个迭代。与上一节 K16 包相比，两次测量结果如下；两组生成 token 均与上一包一致。

| 场景 | 上一包 TPS | 本包两次 TPS |
| --- | ---: | ---: |
| Rust LRU | 37.21 | 38.19／38.91 |
| Python async | 47.45 | 50.70／51.98 |

Rust 场景仍低于更早并行 FP32 归约包的约 44 TPS；该旧包的生成轨迹和草稿接受率不同。本包保留 K16 数值契约，与上一 K16 包输出一致。窄行算子的加速不能直接按比例换算为完整请求收益，Graph 中可重叠的计算及草稿接受率也影响吞吐。

普通 decode 的总 TPS，按并发 1／2／4／8／33，分别为 25.89／43.44／73.55／112.65／166.87。Rust release CLI 加载到就绪 18.28 s；三个热态 512-token 请求合计 prefill 986.6 TPS，单次为 984.7–988.3 TPS。CLI 此项只测 prefill，MTP 数据来自上述完整请求链。

与上一 K16 包对照的固定历史 128 个位置，top3 token 及其概率全部相同，最大目标 NLL 差为 0；这是执行变更对照，量化权重未改。105 组 MTP 状态恢复、文本／单图／双图的 1–7 草稿、多路验证／草稿、28 组混合 batch、Graph／槽位复用、4093→6141-token 前缀恢复和 8192-token 长短请求调度均通过。一组 Python 代码生成关闭 Graph 后，输出也与开启时一致。

执行包已重建，仍为 445 个编译定义、383 个唯一 cubin；全部 buffer 描述和 2739 个不可变权重／数据 payload 保持原样。

## 原生调用绑定模板化

Flash Next 的原生映射采用 656 个共享调用模板、逐层参数表和 369 份共享特化表（635 个表项），不再逐层写出 14,780 条完整绑定记录。生成源码从 2.46 MB 降为 0.97 MB，原生库从 5.91 MB 降为 4.11 MB，执行包从 49.03 MiB 降为 45.89 MiB。发布目录仍包含 445 个编译定义、383 个唯一 cubin；在线导出剔除 998 条未引用的构建绑定，实际注册 13,782 条调用绑定和 378 个 cubin。离线检查保留完整构建契约，以便继续重建。

按绑定名称精确比对重建前后的全部参数、grid、动态 launch、程序、特化选择、Graph 分支及 buffer／请求状态描述，均相同。权重与 cubin 未改。单流同历史 KL、目标 NLL 差为 0，28 组混合请求的 KL 为 0；105 组 MTP 状态检查和 68 组生成 token 序列与原包一致，覆盖文本、单图、多图及 1–7 草稿。Graph／槽位复用和 4093→6141-token 前缀恢复通过。

相同 Rust release 请求链连续复测，普通 decode 并发 1／2／4／8／33 为 26.08／43.33／73.82／112.51／167.14 TPS，与上一包的差异均不到 1%。两组代码生成 MTP，原包为 39.09／51.76 TPS，新包为 39.04／51.83 TPS，输出 token 相同。MTP 统计沿用上一节排除最初三个迭代的口径。

Rust release CLI 三个热态 512-token 请求合计 prefill 原包 987.6 TPS、新包 986.3 TPS；加载到就绪分别 18.29 s、18.16 s。加载为连续进程复测，未清理系统缓存，不作为冷启动加速结论。模板仅参与加载和计划生成，Graph replay 不解释模板，未观察到推理性能回退。
